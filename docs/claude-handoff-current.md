## 2. Architecture / sources of truth

Three-layer model, strictly separated:

- **WooCommerce** (scrollyseo.com, live site) — authoritative for commerce: order/payment facts,
  customer account ownership, product catalog. Never overridden by anything else.
- **`clients/<slug>/order.json`** (file-backed, via `automation/lib/order-state.mjs`) —
  authoritative for fulfillment/workflow state (intake → running → QA → approval → delivery).
  Never trust agent-authored prose for this; only runner/bridge code writes it.
- **WordPress `_scrolly_*` order meta** — a **projection only**, derived one-way from
  `order.json` via `automation/lib/wp-tracker-sync.mjs`. Never a source of truth, never used to
  authorize anything.

Pipeline components:
- **Tally** — intake form (`https://tally.so/r/D4OVlE`), hit after WooCommerce payment verification.
- **n8n** (Docker container, separate from this host) — orchestrates the workflows: intake →
  kickoff, engagement-complete (readiness check + operator/client emails), approve-and-send.
- **Bridge server** (`automation/bridge-server.mjs`, runs natively on Windows) — the only thing
  n8n (in Docker) can reach on this host; also serves the operator dashboard and report PDFs.
- **Discover runner** (`automation/runner/run-discover.mjs`) — the Claude Agent SDK-driven
  research/report-generation process.
- **Operator dashboard** (`automation/dashboard/index.html`, served by the bridge) — internal
  monitoring/QA/approval UI, not customer-facing.
- **Customer tracker projection** — WordPress My Account, via WPCode snippets on the live site
  (not filesystem mu-plugins — see §5).
- **Report/appendix artifacts** — `clients/<slug>/discover/report.pdf` + `appendix.pdf`
  (plus `.md` sources), generated once by the runner, never regenerated by the dashboard.

## 4. Current operator dashboard

Files: [automation/dashboard/index.html](../automation/dashboard/index.html) (single-page
vanilla JS/HTML, dark theme — no framework), served and backed by
[automation/bridge-server.mjs](../automation/bridge-server.mjs), data from
[automation/lib/order-aggregator.mjs](../automation/lib/order-aggregator.mjs).

Routes (all on the bridge server, default port 5679):
- `GET /dashboard` — the HTML page.
- `GET /orders` — list view JSON (all orders with `order.json`, enriched with a best-effort
  live WooCommerce lookup for purchase date/payment status via `lib/wc-order-lookup.mjs`).
- `GET /order-detail?slug=` — detail view JSON, includes DataForSEO capability summary and
  event timeline.
- `GET /report-file?slug=&type=report|appendix` — serves the real PDF from the path recorded
  in `order.json` (never an arbitrary path).
- `POST /approve-and-send` — the dashboard's Approve & Send action (see below).

**List view**: summary cards + a sortable table (WC order #, business, product, purchase date,
internal status badge, customer-facing status, automation/QA/delivery pills, cost, age-in-stage,
last updated, next action). Sorted by a real 7-tier priority (`priorityTier()` in
`order-aggregator.mjs`) — internal failures first, delivered last.

**Detail view**: Commerce / Intake / Automation (incl. DataForSEO capability pass/fail/N-A
breakdown) / QA / Delivery / Cost / Report / Actions / Timeline panels, all from real
`order.json` + WooCommerce fields — nothing estimated or invented.

**Report review**: "Open Report (PDF)" / "Open Appendix (PDF)" buttons hit `/report-file`
directly — no rerun, no rebuild.

**Cost display**: real stored `costUsd` (Anthropic only) shown as `$X.XX`; DataForSEO cost is
explicitly labeled "not tracked structurally yet" (there is no such field anywhere in the
schema — never invented).

**Failure monitoring**: `needs_attention` orders get a dedicated red panel (error class, failed
step, message, report-draft-exists, customer-action-required, retry-available). No retry is
triggered from the dashboard.

**Approve & Send**: `POST /approve-and-send` in `bridge-server.mjs` — re-checks `order.json`
status is genuinely `awaiting_final_review` before doing anything (rejects otherwise, which
also prevents double-send on a second click), calls `recordApproval`, reuses the *existing*
`build-resend-payload.mjs` (client-delivery mode, unchanged) and the same Resend call, then
`mark-delivered.mjs` (unchanged). **This route has never been exercised end-to-end with a real
send** — only its rejection path (invalid state) has been verified live. Do not trigger a real
send without explicit approval.

## 9. Important safety / implementation constraints

- **No funded Discover reruns, and no Anthropic/DataForSEO calls "just to check something"**
  unless explicitly approved for that specific purpose. All 72 tests are free/offline.
- Do not modify the working Discover methodology opportunistically while doing QA/delivery work.
- Do not manually alter WooCommerce order ownership (`customer_id`) — only WooCommerce's own
  native flows (checkout, or verified email-linking) may set it.
- Do not send a real customer email or deliver a real report without explicit approval.
- WooCommerce stays authoritative for commerce/ownership; `order.json` stays authoritative for
  workflow; WordPress `_scrolly_*` meta is a one-way projection only — never reverse this.
- Customer-facing authorization must always derive from WooCommerce's native order ownership
  (`current_user_can('view_order', ...)`) — never from email, order number, slug, or a URL param.
- Reuse existing systems (bridge routes, `order-state.mjs`, `wp-tracker-sync.mjs`,
  `build-resend-payload.mjs`, etc.) instead of building parallel mechanisms.
- Exact dependency/version pinning matters: `dataforseo-mcp-server` is pinned to `3.1.1`
  (see `.mcp.json` / `automation/runner/run-discover.mjs`) after a real v2→v3 breaking change
  broke the pipeline earlier in this project. Don't bump it casually.
- WordPress code changes go live via **WPCode snippets through the wp-admin UI** — there is no
  SFTP/file-based deployment path to scrollyseo.com. Mirror any live edits back into
  `automation/wordpress/deployed/` for version history.
- Live WordPress/browser automation in this environment has been unreliable for rapid,
  unattended page-by-page navigation (see §7) — verify visually-sensitive claims carefully,
  don't trust a single fast pass.
