- **Two independent caches sit in front of every page edit**, and both must be cleared after any content change (via wp-admin, REST, or otherwise) or the live site keeps serving old content: (1) EasyWP's host-level cache — admin-bar "Clear Cache" link (has a nonce, re-find it each time); (2) **Elementor's own render/data cache** (separate from EasyWP's) — Elementor → Tools → "Clear Files & Data". Discovered because a direct REST API edit to a page's content updated the DB correctly but the live site kept rendering the old HTML until the Elementor-specific cache was cleared too.
- **Gitignore gap:** `products/shopify-seo-workbook/build/node_modules/` is NOT covered by `.gitignore` (only `automation/node_modules/` is). Add it before ever running a broad `git add`, to avoid accidentally committing a large node_modules tree.
- **Workbook PDF pagination — `@page{margin:0}` + Puppeteer footer overlay is a real footer-collision trap.** `render-pdf.mjs` draws page numbers/footer text via Puppeteer's `footerTemplate`, which reserves space via the JS `margin` option — but `build/workbook.css`'s `@page` rule needs its OWN matching bottom margin too, or Chrome's content pagination has zero awareness of the footer band and will happily lay text out underneath it (confirmed: 19 of 121 pages had genuine text-through-footer collisions before this was caught). Fixed via `@page{margin:0 0 0.4in 0}` — but two page types (`.cover2` cover, `.popener2` Part-openers) need true edge-to-edge bleed, which a page margin normally breaks; solved with CSS named pages (`@page fullbleed{margin:0}` + `page: fullbleed` on those two classes) rather than negative margins (tried first — didn't work, left a 0.4in gap at the bleed page's bottom and bled a stray sliver onto the next page's top). If this pipeline is touched again, verify collisions weren't reintroduced by extracting text-span y-coordinates from the rendered PDF (e.g. via PyMuPDF/`pymupdf`, already installed on this machine) and checking nothing overlaps the footer's y-range — screenshot-based QA proved unreliable (the in-app browser's PDF-viewer automation repeatedly froze/glitched this session).
